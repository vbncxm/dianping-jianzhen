# 虚假评论清洗后端（backend/）

「线上虚假评论检测数据分析系统」的后端：对抓取到的携程评论做**虚假评论检测 → 净化清洗 → 酒店评分重算**，
并把净化结果输出给前端榜单页面消费。

---

## 一、它解决什么问题

原榜单的口碑分直接对全部评论求均值，存在两个失真：

1. **刷评污染**：模板化、爆发聚集、跨店刷手等评论会把分数抬高；
2. **时间维度缺失**：原脚本因为拿不到评论日期，时间衰减因子只能取中性值 `1.0`，
   一家三年前口碑很好的店和一家上个月刚火起来的店得分一样。

后端把这两件事都修了：先把可疑评论识别出来剔除／降权，再用**真实评论日期**算时间衰减。

## 二、五类检测信号

| 维度 | 权重 | 判定依据 |
|---|---|---|
| 文本痕迹 | 0.30 | 营销夸张词、字符 bigram 模板雷同、整条文本完全重复、标点／表情堆砌、套话齐夸且无细节、极短且无信息量 |
| 时间行为 | 0.25 | 单日爆发聚集（≥日均 3 倍且 ≥4 条）、深夜发布、同一账号同日连发、评论与入住时间错位 |
| 账号行为 | 0.25 | 同一昵称跨店刷评、跨省活跃、活跃天数异常、随机串昵称 |
| 评分异常 | 0.15 | 满分但正文空洞、维度分与总分矛盾、推荐意愿与评分矛盾、全五星无区分度 |
| 图文一致性 | 0.05 | 声称实拍却无图、多图配空洞正文 |

**合成方式**（关键设计）
每个子信号先算 0~1 强度，乘各自「增益 g」后，在同一维度内用**模糊或**累积：

```
维度分 = 1 - Π(1 - sᵢ · gᵢ)
```

这样单个强证据（如整条文本完全重复、同账号跨店刷评）就能把该维度抬到 0.8 以上，
不会被一堆弱信号的平均值稀释掉。五维加权 ×100 得风险分，命中「定罪级」标签再乘 1.25 并 +8。

**清洗策略**

| 风险分 | 等级 | 处理 |
|---|---|---|
| ≥ `high_threshold`（默认 60） | 高风险 | 剔除，不参与评分（清洗权重 = 0） |
| ≥ `watch_threshold`（默认 35） | 观察 | 线性降权，最多削 70% |
| 其余 | 低风险 | 保留，权重 1.0 |

> 阈值按本样本风险分分布校准：高风险 ≈ P99.6，观察 ≈ P96。

## 三、评分公式

```
性价比指数 =（评论质量 × 情感得分 × 设施得分）× 时间衰减因子 × 价格弹性系数 ÷ 价格
```

| 因子 | 计算方式 |
|---|---|
| 评论质量 | AHP 加权：总评分×0.40 + 客房分×0.30（代理卫生+环境）+ 设施分×0.15 + 服务分×0.15；**只统计净化后保留的评论**并按清洗权重加权；再向全站先验分做贝叶斯收缩（C=30） |
| 情感得分 | 每条 = 星级归一×0.60 + 词典文本极性×0.25 + 是否推荐×0.15，按清洗权重加权 |
| 设施得分 | 净化后设施分 ÷ 5 |
| **时间衰减因子** | `Σ exp(−λ·Δtᵢ)·wᵢ / Σ wᵢ`，Δt 为评论距基准日的天数，λ=0.001 ← **真实日期** |
| **价格弹性系数** | `clamp((P / P̄)^θ, 0.70, 1.40)`，P̄ 为区内中位价，θ=0.30 ← **价格敏感度递减**，避免榜单被绝对最低价主导 |

## 四、目录结构

```
backend/
├── config.py     配置（权重 / 阈值 / 公式参数），运行时可被 API 覆盖
├── lexicon.py    词库（营销夸张词 / 情感词 / 具体性词 / 套话模板 / 通用昵称）
├── loader.py     读取 reviews/all_reviews.jsonl 与酒店元信息
├── features.py   单条评论特征抽取（含倒排表加速的模板相似度）
├── detector.py   五类信号融合 → 风险分 / 等级 / 证据标签 / 清洗权重
├── scorer.py     净化后酒店评分 + 区内排名
├── store.py      SQLite 持久化（特征列 zlib 压缩，98MB → 13.5MB）
├── pipeline.py   端到端编排 + 导出 refined_scores.json
├── api.py        FastAPI 接口 + 托管前端
├── serve.py      启动入口
└── data/
    ├── cleaner.db            SQLite 库（runs / reviews / hotel_scores / evidence_stat）
    ├── refined_scores.json   前端消费的净化结果
    └── flagged_reviews.json  全量评论风险判定
```

## 五、用法

### 1. 跑一遍清洗与评分

```bash
cd 榜单生成
python -m backend.run                    # 默认参数
python -m backend.run --high 55          # 调低高风险阈值
python -m backend.run --no-persist       # 只算不写库
```

可选参数：`--high` `--watch` `--max-downweight` `--keep-high`
`--lambda-decay` `--theta` `--bayes-c` `--as-of`

### 2. 重建前端页面（读取净化结果）

```bash
python 03_build_pages.py
```

页面会自动带上「后端评论净化」区块（净化率、五因子、风险评论明细）与总榜净化徽标。
若 `backend/data/refined_scores.json` 不存在，页面会跳过该区块并提示。

### 3. 启动后端服务（接口 + 前端一体）

```bash
python -m backend.serve                  # http://127.0.0.1:8000
python -m backend.serve --port 8080 --analyze   # 启动前先跑一次分析
```

- 接口文档：`/docs`
- 榜单前端：`/`

## 六、主要接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查、当前批次 |
| GET | `/api/stats` | 全局统计（风险分布、证据 TOP、净化率） |
| GET | `/api/config` | 读取当前检测配置 |
| PATCH | `/api/config` | 改配置并重跑（body: `{"patch": {...}}`） |
| POST | `/api/analyze` | 用指定参数重跑，不落库 |
| GET | `/api/rankings?district=&top=` | 各区净化后榜单 |
| GET | `/api/hotels` | 酒店列表（净化前后评分） |
| GET | `/api/hotels/{id}` | 单店详情 + 风险评论明细 |
| GET | `/api/hotels/{id}/reviews?level=&limit=` | 单店评论（带风险判定） |
| GET | `/api/reviews?level=&hotel=&limit=` | 全量评论检索 |
| GET | `/api/evidence` | 证据标签命中统计 |
| GET | `/api/runs` | 历史批次（可对比不同阈值的效果） |

示例：

```bash
curl 'http://127.0.0.1:8000/api/rankings?district=呈贡区&top=5'
curl 'http://127.0.0.1:8000/api/reviews?level=高风险&limit=20'
curl -X PATCH http://127.0.0.1:8000/api/config \
     -H 'Content-Type: application/json' \
     -d '{"patch":{"high_threshold":55}}'
```

## 七、当前结果（样本：25 家榜单酒店 · 7534 条评论）

- 高风险 **15** 条（0.20%）、观察 **268** 条（3.56%）、整体净化率 **1.17%**
- 命中最多的证据：满分但正文空洞 1200 条、极短且无信息量 460 条、标点／表情堆砌 431 条
- 时间衰减因子落在 **0.55 ~ 0.90**（原脚本固定为 1.0），使榜单明显偏向近期口碑稳定的店
- 净化后名次变动示例：盘龙区「大良日式诧寂民宿」升至第 1、「云源酒店」因评论偏旧降至第 4；
  呈贡区「铭缘宾馆」净化率 5.3%，从第 1 降至第 2

## 八、已知局限

- **短评不等于假评**。样本里「安静，适合备考人」「视野广阔👍」这类短评是真实用户的正常表达，
  因此「极短」只作为弱辅证（增益 0.35），必须与满分、无细节、爆发等信号叠加才起效。
- **时间爆发**可能误伤真实热点（如考试季考点周边酒店集中入住后集中评价），
  故单日爆发仅列为证据、由多信号共同决定。
- **账号维度**受限于数据：`合作平台用户`「匿名用户」等通用昵称无法跨店追踪（占 14.6%），
  这些评论的账号维度直接置 0，不参与判定。
- 检测结果是**疑似排序**，不是事实认定；前端文案统一表述为「疑似／已剔除降权样本」。
